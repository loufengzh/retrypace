# Начало работы с retrypace

[English](../README.md) · [中文](zh-CN.md) · [Deutsch](de.md)

retrypace — автономный анализатор расписаний повторных запросов для обсуждения архитектуры и CI. Он показывает, сколько полных попыток помещается в срок, сколько запросов выполняется одновременно и насколько велики всплески запусков в скользящем окне.

Требуется Python 3.10 или новее. Нет зависимостей времени выполнения, сетевых запросов, телеметрии или настоящих задержек.

## Запуск

```sh
git clone https://github.com/loufengzh/retrypace.git
cd retrypace
python -m retrypace --config examples/burst.json --compare
python -m retrypace --config examples/staggered.json --format csv > attempts.csv
python -m unittest discover -s tests -v
```

Установка для запуска из исходников не нужна. Необязательная локальная установка: `python -m pip install .`; средства сборки могут потребовать загрузки. После неё доступна команда `retrypace`. Проект пока не опубликован в PyPI: одноимённый пакет в реестре не следует считать этим проектом.

## Конфигурация

Создайте JSON-файл. Пропущенные поля получают следующие значения по умолчанию. Время задаётся целым числом миллисекунд.

```json
{
  "clients": 100,
  "max_attempts": 5,
  "base_ms": 100,
  "cap_ms": 2000,
  "attempt_ms": 50,
  "deadline_ms": 3000,
  "stagger_ms": 0,
  "window_ms": 100,
  "concurrency_limit": 20,
  "seed": 1,
  "strategy": "full-jitter"
}
```

- `clients`: количество клиентов.
- `max_attempts`: предел общего числа попыток, включая первоначальный запрос.
- `base_ms`, `cap_ms`: базовая задержка и её потолок; потолок не меньше базы.
- `attempt_ms`: фиксированная положительная длительность попытки.
- `deadline_ms`: бюджет каждого клиента относительно его старта. Попытка допускается только целиком; завершение точно в срок разрешено. Нулевой бюджет не допускает запросов.
- `stagger_ms`: интервал между стартами соседних клиентов; ноль означает одновременный старт.
- `window_ms`: ширина окна подсчёта запусков.
- `concurrency_limit`: справочный порог для измерения превышения, а не семафор. Он не создаёт очередь и не отклоняет запросы.
- `seed`: воспроизводимое начальное значение от 0 до 2³²−1.
- `strategy`: `fixed`, `exponential`, `full-jitter`, `equal-jitter` или `decorrelated`.

Все числа, кроме срока, интервала стартов и seed, должны быть положительными целыми. Булевы значения вместо чисел не принимаются. Верхняя граница остальных чисел — 1 000 000 000. Неизвестные поля вызывают ошибку. Произведение `clients × max_attempts` ограничено 1 000 000; большие отчёты всё равно могут потребовать много памяти.

## Модель и стратегии

Все допущенные попытки считаются неуспешными. Ожидание начинается после завершения запроса. Каждый клиент повторяет запросы последовательно и не влияет на других. Экспоненциальный потолок первой повторной попытки равен базе, затем удваивается до `cap_ms`.

- `fixed`: постоянная базовая задержка.
- `exponential`: текущий экспоненциальный потолок.
- `full-jitter`: целочисленное значение от нуля до этого потолка.
- `equal-jitter`: от половины потолка с округлением вверх до полного потолка.
- `decorrelated`: от базы до тройной предыдущей задержки, затем ограничение потолком. Исходная предыдущая задержка равна базе.

Обе границы случайного интервала включены. Одинаковые входные данные и seed дают одинаковый результат. Генератор не криптографический; это не готовая рекомендация для реализации повторов в продакшене.

## Как читать отчёт

JSON содержит `schema_version`, `model`, `config`, `summary`, `buckets` и, при необходимости, `events`.

- `attempts` / `retries`: все допущенные запросы / только повторы.
- `clients_stopped_by_deadline`: клиенты, у которых следующая полная попытка уже не помещается в бюджет.
- `clients_stopped_by_attempt_limit`: клиенты, исчерпавшие число попыток.
- `peak_concurrency`: максимальное число одновременно выполняющихся запросов. Интервалы полуоткрытые `[начало, конец)`: запросы, заканчивающиеся и начинающиеся в один момент, не перекрываются.
- `peak_window_starts`: максимум запусков в любом полуоткрытом окне; обнаруживает всплески на границах фиксированных интервалов.
- `peak_aligned_bucket_starts`: максимум по фиксированным интервалам, выровненным относительно глобального нуля. Пустые интервалы не выводятся.
- `retry_peak_concurrency` / `retry_peak_window_starts`: те же пики без первоначальных запросов.
- `time_over_concurrency_limit_ms`: суммарное время строгого превышения порога.
- `excess_concurrency_ms`: интеграл превышения количества запросов над порогом, в запросо-миллисекундах.
- `max_client_elapsed_ms`: максимальное время от старта клиента до окончания его последнего допущенного запроса.
- `min_client_budget_remaining_ms`: минимальный остаток бюджета после последнего допущенного запроса.
- `schedule_end_ms`: последнее глобальное завершение с учётом разнесённых стартов.

В `examples/burst.json` full jitter снижает пик параллельных повторов со 100 до 51, но увеличивает число повторных запусков в самом загруженном окне 100 мс со 100 до 109. Короткие задержки позволяют выполнить больше повторов. Первоначальный всплеск из 100 одновременных запросов остаётся у всех стратегий. Один seed не даёт статистического доказательства превосходства стратегии.

## CLI и CI

```sh
python -m retrypace --config examples/burst.json --summary-only > report.json
python -m retrypace --config examples/burst.json --strategy exponential
python -m retrypace --config examples/staggered.json \
  --max-peak-concurrency 50 --max-window-starts 200 > report.json
```

Проверки порогов учитывают и первоначальные запросы. Равенство допустимо; строгое превышение означает ошибку проверки. При `--compare` достаточно превышения у одной стратегии. Отчёт сохраняется в stdout даже при превышении; пояснение направляется в stderr. CSV содержит `client,attempt,start_ms,end_ms` и несовместим с `--compare` и `--summary-only`.

Коды завершения: 0 — успех, 1 — конфигурация недоступна или некорректна, 2 — превышен порог либо неверные аргументы CLI. Доступны `--help` и `--version`. `--summary-only` уменьшает вывод, но не память для анализа.

## Библиотека

```python
from retrypace import Config, compare, simulate

config = Config(clients=30, max_attempts=4, deadline_ms=1000, seed=42)
report = simulate(config)
print(report["summary"]["retry_peak_concurrency"])
policies = compare(config)
```

`Config` — неизменяемая структура с проверкой входных данных. `Config.from_dict(mapping)` принимает конфигурацию из словаря. `simulate(config, include_events=False)` исключает подробные события из отчёта. `compare` возвращает отображение названий стратегий в отчёты.

## Ограничения

Это аудит заданного сценария, не прогноз восстановления, теория очередей или нагрузочный тест. Здесь нет успешных запросов, восстановления сервиса, переменной задержки, реального ограничения скорости, Retry-After, вложенных повторов, отмены или проверки идемпотентности. Порог параллелизма не меняет расписание. Проверяйте производственные настройки нагрузочными тестами и телеметрией.

[Retry Lab](https://github.com/kyan9400/retry-lab) моделирует восстановление интерактивно в браузере; retrypace сосредоточен на автономном аудите сроков и давления. Стратегии описаны в [статье AWS](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/); код других проектов не копировался. [Точная модель на английском](model.md).
